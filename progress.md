- One deterministic canonical serializer per evidence type (`text`, `table`, `visual`) in `kpi_crawler/evidence_serialization.py`: pure functions of an evidence item's own claim/value/supporting_context/structure, unconfigurable per source/document/KPI, performing no relevance ranking, and carrying a shared `CANONICAL_SERIALIZER_VERSION`.
- `evidence.canonical_text` and `evidence.canonical_serializer_version` columns (migration `0005_evidence_canonical_text.sql`) storing the serializer's output and version alongside the unchanged, independently preserved richer payload (`supporting_context`, `structure` JSONB).
- `AcquisitionRepository.create_evidence` computes the canonical text at persistence time and stores it with every evidence row; `get_evidence` returns it as part of `Evidence`.
- Five clearly distinguished failure categories, each its own exception type: `AcquisitionError` (fetch failures), `ExtractionError` (parse failures), `StorageError`/`DatabaseError` (raw-artifact filesystem and PostgreSQL persistence failures), `UnsupportedContentError` (content type not in the allowed set), and `OperationalLimitError` (a configured bounded-resource limit reached) — all defined in `kpi_crawler/errors.py`.
- Bounded resource controls on acquisition: request timeout and retry count (already present, now configurable), maximum artifact size enforced *before* unbounded buffering (declared `Content-Length` checked first for HTTP; local files `stat()`-checked before reading; bounded `read()` as a fallback when no length is declared), and an allowed content-type set enforced after acquisition, before extraction is attempted.
- Raw-artifact filesystem writes (`_write_raw` in `kpi_crawler/acquisition.py`) now catch `OSError` and raise `StorageError` instead of leaking an unhandled exception.
- `run_pdf_pipeline` (`kpi_crawler/pipeline.py`) commits progressively at durable checkpoints — run created, artifact acquired and stored, evidence persisted — so a later-stage failure (unsupported content, extraction failure, or an evidence-persistence storage failure) rolls back only its own in-flight attempt and can never discard an artifact a prior stage already, successfully, committed. Every failure path makes a best-effort attempt (`_record_failure`) to record a `failed` acquisition/extraction event and complete the run as `failed`; a secondary storage failure while recording is logged and swallowed rather than masking the original error.
- `Settings` (`kpi_crawler/config.py`) gained validated environment overrides for the new bounded controls: `ACQUISITION_TIMEOUT_SECONDS`, `ACQUISITION_RETRIES`, `MAX_ARTIFACT_BYTES`, `ALLOWED_CONTENT_TYPES` (comma-separated). The CLI `process` command wires these through and logs a category-labeled outcome (`acquisition failed` / `rejected: unsupported content` / `rejected: limit exceeded` / `extraction failed` / `storage failed`) with a `discovered=/acquired=/rejected=` summary; the durable, queryable report is `app.acquisition_runs`/`app.acquisition_events`.
- Generalized web discovery and navigation (`kpi_crawler/discovery.py`, `kpi_crawler/crawl.py`), stdlib-only (`html.parser.HTMLParser`, `xml.etree.ElementTree`) — no Crawlee or Playwright: no fixture demonstrated that plain HTTP/HTML acquisition cannot obtain a required resource, so a browser-execution dependency was not justified, and the discovery needs (link/sitemap/robots.txt parsing) are simple enough that stdlib parsing is the "simplest reliable approach" without Crawlee's added surface.
- `kpi_crawler/discovery.py` — pure, I/O-free parsing: `extract_html_links` (`<a href>`/`<link href>`, resolved and defragmented against a base URL, restricted to followable schemes `http`/`https`/`file`/relative — not `mailto:`/`javascript:`/etc.); `extract_sitemap_locations` (`<loc>` entries from a sitemap or sitemap index, namespace-agnostic); `extract_robots_sitemap_urls` (`Sitemap:` directives, RFC 9309); `discover_links` dispatches by content type (and, for robots.txt, by its fixed well-known path) — never by a discovered resource's filename. Pagination is recognized only via the standards-based `rel="next"` attribute (`<a>` or `<link>`), never inferred from link text, CSS class, or position — no heuristic classification of any kind.
- `kpi_crawler/pipeline.py` was refactored so the per-URL "acquire, store, extract-if-supported" logic is the shared `_process_source`, returning a `FetchOutcome` instead of always raising, so a caller processing many URLs (the crawler) can record a per-URL failure and keep going instead of aborting. `_process_source` unconditionally skips extraction (via `AcquisitionRepository.artifact_has_extraction`) when this artifact's content was already successfully extracted — content-level deduplication layered on top of the pre-existing SHA-256 artifact-level dedup, so the same bytes reached via two different URLs, or the same URL processed twice, never produce duplicate evidence. (This was originally crawler-only and opt-in; the engineering-review pass below made it unconditional after finding it was needed for `run_pdf_pipeline`/`process` too.)
- `kpi_crawler/crawl.py` — `run_crawl` performs one breadth-first crawl per call, one `acquisition_runs` row for the whole crawl: seeds the queue with the root URL plus (for `http`/`https` roots) the well-known `/robots.txt` and `/sitemap.xml` paths; URL-level deduplication via a per-run visited set (fragment-insensitive, query-sensitive); crawl depth bound (`max_depth`, default 2) applied **per discovered link**, not per page, so a `rel="next"` pagination link stays at its source page's depth while an ordinary link increments it — pagination is therefore not depth-limited the way nested pages are; a `max_artifacts` bound (default 50) that stops further acquisition once reached, recording each skipped URL as a `discovery`/`failed` event rather than fetching it; a `same_host_only` bound (default `True`) that rejects off-host discovered links by netloc comparison alone, before any network call. Acquisition lineage is the existing `acquisition_events.parent_event_id` chain — a discovered URL's event points at the acquisition event of the page it was found on — so no schema change was needed. `CrawlResult` reports `discovered`/`acquired`/`rejected` counts plus a per-page result list; the durable, queryable audit trail remains `app.acquisition_runs`/`app.acquisition_events`.
- `Settings` gained `CRAWL_MAX_DEPTH` and `CRAWL_MAX_ARTIFACTS` (validated, same pattern as the other bounded controls). New CLI command `crawl <source-url>` wires everything through and logs a `discovered=/acquired=/rejected=` summary.
- No relevance scoring, semantic page classification, university-specific heuristics, filename-based filtering, priority tiers, or a relevance classifier were added anywhere in this phase — every discovered, in-bounds URL is acquired uniformly regardless of what it is.
- `kpi_crawler/export.py` — `export_run(run_id, database_url, export_dir)`: a read-only, self-contained, human-readable snapshot of one completed run, for showing results outside PostgreSQL. Not a new storage layer or processing pipeline: PostgreSQL remains canonical, raw artifact files remain canonical, and export only serializes what `AcquisitionRepository` already returns — no new extraction, no re-parsing, no relevance/ranking logic. Two small, purely-read repository methods were added to support it: `get_run` (mirrors the existing `get_artifact` not-found convention) and `list_evidence_for_artifact` (mirrors `get_evidence`'s existing join query, filtered by artifact instead of by evidence id). A "source" is one distinct acquired artifact within the run (keyed by its stable `artifacts.id`, not an invented ID scheme); a URL that failed before an artifact ever existed (acquisition failure, or a crawl's off-host/limit rejection) is listed under `manifest.json`'s `rejected` array and in the README's "Rejected or failed resources" section instead of getting a `sources/<id>/` directory, since there is nothing to export for it.
- Export structure: `<EXPORT_DIR>/run-<run_id>/{README.md, manifest.json, sources/<artifact_id>/{source.json, original.<ext>, evidence.jsonl}}`. `README.md` is plain-language (root/source URL, run ID/timestamps/status, discovered/acquired/rejected counts, artifacts by type, extraction succeeded/no-evidence counts, total evidence count, what an evidence record is and how it traces back to its source, and a list of included sources). `manifest.json` holds the same facts machine-readably, plus every source's full acquisition-event and extraction-event history within the run. `evidence.jsonl` is one JSON object per line, a direct, unmodified serialization of `EvidenceProvenance` (evidence id/type/claim/value/supporting_context/structure/canonical_text/canonical_serializer_version plus source_url/page_number/location/extractor/extractor_version) — the persisted database representation, not reconstructed. `original.<ext>` is a plain `shutil.copyfile` of the artifact's `raw_storage_ref` (extension derived from content type, with a small override table for the common cases since Python's `mimetypes` maps `application/xml` to the surprising `.xsl`); if the raw file is missing on disk (the previously-documented stale-`raw_storage_ref` scenario), export continues and `source.json`/`manifest.json` record `original_artifact.included: false` with a reason instead of silently omitting it or failing the whole export.
- Export never writes to PostgreSQL (verified) and is safe to re-run: the package is built in a temporary sibling directory (`tempfile.mkdtemp(dir=export_dir, ...)`) and only atomically swapped into place (`Path.replace`, after removing any prior `run-<id>/`) once every file has been written successfully, so a crash mid-export or a repeated export can never leave a half-written or merged/stale package at the final path. A failure during writing cleans up its temp directory before propagating.
- New `ExportError` (`kpi_crawler/errors.py`, an `ApplicationError`) for an unknown run ID; it falls into the CLI's existing generic `ApplicationError` catch-all, so no change to the CLI's exception-handling chain was needed. New CLI command `kpi-crawler export <run-id>` and `Settings.export_dir`/`EXPORT_DIR` (default `exports`, same validated-settings pattern as `ARTIFACT_STORAGE_DIR`).

## Engineering review (2026-09-19)

A full read-through of every module in `kpi_crawler/` and `tests/` looking for bugs, incorrect assumptions, broken error handling, race conditions, data integrity problems, missing constraints, provenance gaps, duplicate logic, unnecessary abstractions, poor test coverage, security issues, resource leaks, inconsistent interfaces, and undocumented behavior. Concrete problems were fixed; things that were merely hypothetical were recorded instead (see "Unresolved issues").

**Data integrity (the most serious finding, concretely reproduced, not hypothetical):** running `kpi_crawler process` twice on identical content silently created a second `extractions` row and a full second copy of that document's evidence — reproduced directly: two `process` calls against the same file produced `evidence` count 2 where it should have been 1. The crawler had already solved this for itself (an opt-in `skip_if_already_extracted` flag added in the discovery-navigation phase), but the single-URL pipeline never used it, so `process`/`run_pdf_pipeline` was still exposed. Fixed at two levels: (1) `_process_source` now unconditionally skips re-extraction when `AcquisitionRepository.artifact_has_extraction` reports the artifact already has a successful extraction — no more opt-in flag, since no caller wanted the old behavior; (2) a new partial unique index, `extractions_succeeded_artifact_idx ON app.extractions (artifact_id) WHERE status = 'succeeded'` (migration `0007`), makes a second concurrent writer's duplicate `succeeded` extraction a clean, already-handled `DatabaseError` instead of silently succeeding — closing the residual race between two concurrent processes both passing the application-level check before either commits. Verified directly: a second `INSERT ... status='succeeded'` for the same `artifact_id` is rejected by Postgres with `duplicate key value violates unique constraint`, while a `failed`-status row for the same artifact is unaffected. A regression test (`test_reprocessing_identical_content_does_not_duplicate_evidence`) processes the same content twice and asserts the second call returns no new evidence and exactly one `succeeded` extraction row exists.
**Resource leaks (three found and fixed):**
- `PdfExtractor.extract` never released the Docling `PdfDocument` it loads. Docling's own API exposes an explicit `document.unload()` (confirmed present and working via direct interactive testing) rather than relying on Python GC for its native resources; extraction now runs in a `try`/`finally` that always unloads the document.
- `_read_http`'s retry loop caught `HTTPError` to inspect `.code` but never closed it, leaving its underlying socket open until garbage collection — on a long crawl hitting many failing/retryable URLs this accumulates. Now closed in a `finally` on every retry/failure path.
- `_write_raw` could leave an orphaned temporary file on disk if `os.replace` failed after the temp file was already written (e.g., a permission or cross-filesystem issue) — the failure path now unlinks the temp file before raising `StorageError`.

**Security (one found and fixed):** `extract_sitemap_locations` parsed untrusted, crawler-fetched XML with `xml.etree.ElementTree.fromstring`, which does not fetch external entities but does still expand internal ones — a small, crafted "sitemap.xml" served by any crawled host could trigger a classic entity-expansion ("billion laughs") memory-exhaustion DoS against the crawler process; the existing `max_artifact_bytes` cap does not protect against this (the attack payload is tiny, expansion happens in memory during parsing). Fixed by rejecting any document containing `<!DOCTYPE` or `<!ENTITY` before parsing — a real sitemap never legitimately needs either.

**Correctness / incorrect assumptions (two found and fixed):**
- `ALLOWED_CONTENT_TYPES` (env-configured) was compared byte-for-byte against `content_type`, which is always lowercase elsewhere in the system (`email.message.Message.get_content_type()` already normalizes HTTP responses to lowercase) — an operator setting `ALLOWED_CONTENT_TYPES=Application/PDF` would have every PDF silently rejected as "unsupported." Now lowercased at parse time, consistent with how content types are represented everywhere else.
- `crawl._normalize` (the per-run URL dedup key) and the `same_host_only` check both compared scheme/host case-sensitively, though both are case-insensitive per RFC 3986 §6.2.2.1 — a site linking to itself with inconsistent host/scheme casing (common enough in the wild) would be crawled as if it were two different hosts/pages. Both now fold scheme and host to lowercase before comparing (path and query are correctly left alone, since those *are* case-sensitive).

**Missing constraint (found and fixed):** `acquisition_events.event_type` had no constraint on its value, unlike `evidence.evidence_type`, which the codebase already established should be a small controlled set. All three actual values in use (`acquisition`, `extraction`, `discovery`) were confirmed by an exhaustive grep before adding migration `0006`'s `CHECK (event_type IN ('acquisition', 'extraction', 'discovery'))`. **Caught its own bug during verification:** the first version of this migration named the new constraint `acquisition_events_event_type_check`, which collided with PostgreSQL's auto-generated name for the *existing*, already-present, unnamed `CHECK (length(event_type) > 0)` constraint on the same column — the migration failed with "constraint already exists" on a truly fresh database. Caught by the "verify from a clean database" step required by this pass (not by unit tests, which had reused a warm database and missed it); fixed by renaming to `acquisition_events_event_type_allowed_check` and re-verified on a fresh database.

**Undocumented behavior (found and fixed):** `FetchOutcome.status`/`CrawlPageResult.status` were plain `str` with no enumeration of their five possible values anywhere; a reader had to trace the whole function body to discover them. Now a `Literal["acquired", "duplicate_content", "unsupported_content", "acquisition_failed", "extraction_failed"]` type alias (`FetchStatus`), each value commented with what it means, shared by both dataclasses.

**Minor inconsistency (found and fixed):** the HTTP `User-Agent` header was a hardcoded, already-stale literal (`"kpi-crawler/0.1"` vs. the package's actual `__version__ = "0.1.0"`). Now derived from `kpi_crawler.__version__` so it can't drift again.

**Poor test coverage (found and fixed):** `kpi_crawler/cli.py` — the module wiring together settings, argument parsing, and the exception→exit-code mapping used by every command — had zero direct tests across every phase that touched it; only ever exercised indirectly through manual smoke tests. Added `tests/test_cli.py` (17 tests, no DB required): argument parsing for all four commands, missing-`DATABASE_URL`/missing-source-url handling, and — the part that actually mattered, since it silently changed shape across several phases — that each of `AcquisitionError`, `UnsupportedContentError`, `OperationalLimitError`, `ExtractionError`, `StorageError`, and `DatabaseError` raised from the pipeline/crawl functions is caught and turned into a clean exit code 1, never an unhandled traceback. Also added: two `AcquisitionRepository` guard-clause tests that had no coverage (`complete_run`/`get_artifact` raising `LookupError` for an unknown id), a direct test that the new `event_type` CHECK constraint actually rejects an invalid value, and four pure unit tests for `crawl._normalize`'s case-folding fix.

**Reviewed and found already correct, no change made:** the `store_artifact` insert-then-select-on-conflict pattern is safe under concurrent writers (Postgres serializes the conflicting inserts via the unique index; the documented "check-then-act" shape is not actually racy); the CLI's exception-handling order (most specific before the general `ApplicationError` catch-all); `db.py`'s connection context manager closes on every exit path; `_read_bounded`'s Content-Length handling degrades safely to a real bounded read even given a malformed or lying header; the migration runner's advisory-lock + checksum design.

**Considered, deliberately not changed (recorded below under "Unresolved issues" instead):** SSRF exposure inherent to "a crawler fetches URLs it's told to fetch"; the `max_bytes` (internal, `acquisition.py`)/`max_artifact_bytes` (public, everywhere else) naming difference; `discover_links` not recognizing `application/xhtml+xml` as HTML; the narrowed provenance model when extraction is deduplicated.

## Run export (2026-09-19)

### CLI usage

```
kpi-crawler export <run-id>
```

`<run-id>` is the integer `acquisition_runs.id` (the same id `crawl`/`process` log at completion, e.g. `crawl run 1 complete`). Writes to `<EXPORT_DIR>/run-<run-id>/` (`EXPORT_DIR` defaults to `exports`, next to `ARTIFACT_STORAGE_DIR`'s default of `.data/artifacts`; both are configurable the same way). On success, logs the output path and a one-line summary (source/evidence/rejected counts). A missing or non-numeric run ID, or a run ID that doesn't exist, is reported as a clean error and exit code 1 — never a traceback.

### Export structure

```
exports/
└── run-<run_id>/
    ├── README.md              # plain-language summary, for a non-developer
    ├── manifest.json          # the same facts, machine-readable, plus full event history
    └── sources/
        └── <artifact_id>/     # one directory per distinct acquired artifact in the run
            ├── source.json        # this artifact's metadata + its acquisition/extraction events in this run
            ├── original.<ext>     # byte-identical copy of the raw artifact (omitted + explained if missing)
            └── evidence.jsonl     # one JSON object per persisted evidence row (empty if none)
```

A source directory is keyed by the artifact's own stable database ID — not an invented numbering scheme — so it can always be cross-referenced directly against `app.artifacts` if needed. Resources that were discovered but never became an artifact (a failed fetch, or a crawl's off-host/limit rejection) are listed in `manifest.json`'s `rejected` array and the README's "Rejected or failed resources" section, not given a `sources/` directory, since there is nothing acquired to export for them.

### Tests

`tests/test_export_integration.py` (12 tests, PostgreSQL required) against a small realistic crawled site (home page, a real downloadable PDF, an unsupported-content `.txt` resource, and a 404): directory structure, multiple sources in one run, byte-identical raw-artifact copies, evidence.jsonl matching `AcquisitionRepository.list_evidence_for_artifact` field-for-field, full source-URL→original→evidence→page/location traceability, a source with zero evidence still getting a directory, a failed acquisition appearing under `rejected` and never under `sources/`, README/manifest content checks, safe re-export (a stray file placed in an existing export does not survive a re-export), a nonexistent run ID raising `ExportError`, and a missing raw artifact file being recorded in `source.json` rather than failing the export. Plus 5 new CLI-level tests (`tests/test_cli.py`, no DB) for argument handling and the `ExportError`/`DatabaseError` → exit-code-1 path. Three PDF fixtures created for these tests, each with content unique to its own test (avoiding the cross-test content-address collisions documented in earlier phases): `tests/fixtures/export_report.pdf`, `tests/fixtures/export_missing_check.pdf`.

### Validation performed

Ran the full suite (101 tests, clean database, migrations idempotent — export needed no schema change), then re-ran the real-fixture crawl (8 real NIRF PDFs behind a realistic site, from the earlier real-fixture validation phase) and exported the resulting run. Confirmed programmatically: all 8 real PDFs' exported files are SHA-256-identical to their recorded artifact hash; the source_url → original file → evidence.jsonl → page_number/location chain is directly traceable for every PDF source; `acquisition_runs`/`artifacts`/`evidence`/`acquisition_events` row counts were identical before and after three separate export invocations (PostgreSQL is untouched by export); a stray file placed inside an existing export did not survive a re-export of real data, not just the synthetic test case.

### Genuinely observed limitations

- When an artifact's raw file is missing from disk (the pre-existing stale-`raw_storage_ref` characteristic, documented in an earlier phase), the export is not byte-identical for that one source — by definition, nothing can be copied. This is handled correctly (recorded plainly in `source.json`/`manifest.json`, export continues for every other source), not silently hidden, but it means "byte-identical export" is a guarantee conditional on the raw file still existing, which the export layer cannot control or repair.
- `manifest.json`'s `resources_acquired` count is URL/fetch-level (matching what `crawl`/`process` themselves report at completion), while `distinct_sources_exported` (the number of `sources/` directories) is artifact-level. These differ only in the unusual case where the exact same content was reached via two different URLs within one run — both counts are reported explicitly and labeled, rather than picking one and silently discarding the other, but a reader who only skims one number could be confused by the (rare) mismatch.
- Export is not incremental: a re-export always rebuilds the entire package from the current database state, even if nothing changed since the last export. For the run sizes this tool currently produces (tens of sources, thousands of evidence rows) this is fast (well under a second in validation); it was not optimized further since nothing asked for it and premature optimization here would be exactly the kind of invented complexity this task asked to avoid.

## Program 1: adaptive acquisition engine + evidence ledger (2026-09-19)

A second, independent acquisition engine, `kpi_crawler/acquisition_engine/`, coexisting with the existing single-threaded `kpi_crawler.acquisition`/`kpi_crawler.crawl` (unmodified, still the path feeding `app.evidence`/extraction/retrieval). This is deliberately **not** wired into the existing pipeline: it defines "Program 1" — a clean, versioned, stable acquisition contract that a not-yet-built "Program 2" (extraction) will consume, per explicit instruction not to design it around the current extraction/retrieval code.

**Modules:** `contract.py` (the stable, versioned artifact/evidence/decision shapes — `CONTRACT_VERSION = 1`), `ledger.py` (the Evidence Ledger: thread-safe, append-only persistence of every attempt/artifact/adaptive-decision), `proxy.py` (health-tracked proxy pool with quarantine), `sessions.py` (session lifecycle: healthy → unhealthy → retired), `adaptive.py` (per-domain concurrency/backoff policy, thread-safe), `concurrency.py` (`AdjustableGate`, a concurrency limiter whose limit can shrink or grow while threads wait on it — `threading.Semaphore` only supports growing), `http_acquirer.py` (single-attempt HTTP fetch with full outcome classification and real redirect-chain capture via a custom `HTTPRedirectHandler`), `browser_acquirer.py` (Playwright-based fallback + the dynamic-content-shell detection heuristic), `raw_storage.py` (content-addressed storage, same convention as the existing `acquisition.py`), `engine.py` (`AcquisitionEngine`: orchestrates BFS discovery — reusing the existing, pure `kpi_crawler.discovery.discover_links` — concurrent HTTP acquisition, browser escalation, retries/backoff, and ledger recording), `events.py`/`cli.py` (structured events + a live terminal presentation layer, `kpi-crawler-acquire`).

**Storage:** new migration `0010_acquisition_engine_contract.sql`, a separate `acq` schema (`acq.runs`, `acq.artifacts` — immutable, like `app.artifacts` — `acq.attempts`, `acq.adaptive_decisions`), independent of `app.*` so Program 2 never needs to understand crawler internals.

**Explicit states** (`AcquisitionState`): `SUCCESS`, `PARTIAL`, `FAILED`, `RATE_LIMITED`, `ACCESS_DENIED`, `TIMEOUT`, `NETWORK_ERROR`, `BROWSER_ERROR`, `UNSUPPORTED`, `BLOCKED`, `PENDING_RETRY`. A run's status is derived per-URL (`derive_run_status`): all-success → `SUCCESS`, none → `FAILED`, otherwise `PARTIAL` — never collapsed to a single pass/fail bit. Every attempt (success or failure) is its own permanent ledger row; nothing is overwritten by a later retry.

**Real, working subsystems (not stubs):**
- Concurrent HTTP acquisition (`ThreadPoolExecutor` + a per-domain `AdjustableGate`) with real adaptive concurrency: a 429 halves the domain's concurrency (floor `min_concurrency`) and computes a real exponential backoff (capped), actually slept before retrying; sustained success gradually restores concurrency.
- Proxy pool: rotation, failure-threshold quarantine (untested against live proxies — no proxy infrastructure exists in this environment; the pool's health-state machine is exercised directly).
- Session lifecycle: a session goes unhealthy after repeated consecutive failures and is retired/replaced.
- Playwright/Chromium browser escalation: HTTP content is checked with a script-ratio/visible-text heuristic (`dynamic_content_likely`); on a likely SPA shell, the engine switches to a real headless Chromium fetch and stores the **rendered** DOM, not the raw shell. Verified end-to-end against a real local page whose content only exists after a `DOMContentLoaded` script runs.
- **Bug found and fixed during implementation:** Playwright's sync API is confined to the thread that started it (`greenlet.error: cannot switch to a different thread` when called from a different worker thread than the one that launched it) — not documented anywhere obvious, found by the first real multi-threaded browser-escalation test run. `BrowserManager` now marshals every Playwright call through a dedicated single-worker `ThreadPoolExecutor`, so any of the engine's concurrent HTTP workers can request browser acquisition safely.
- The Evidence Ledger's single psycopg connection is shared by every concurrent worker thread; `EvidenceLedger` wraps every statement in one lock and runs in autocommit mode (evidence must survive a crash mid-run).

**New dependency:** `playwright` (plus the Chromium browser binary, downloaded once via `playwright install chromium`, ~300 MB — not tracked in git, an operator/CI setup step).

**Tests** (10 new files, `tests/test_acquisition_engine_*.py`): pure unit tests for the contract's run-status derivation, proxy pool health state machine, session lifecycle, adaptive policy (concurrency halving/floor, exponential/capped backoff, restore-after-N-successes, per-domain independence), the `AdjustableGate` under real concurrent thread load, the dynamic-content heuristic, and CLI event-to-text rendering (verbose vs. normal); DB-integration tests for the ledger (artifact/attempt roundtrips, immutability trigger, failure history never overwritten, `SUCCESS`/`PARTIAL` derivation, concurrent-thread-safety); and two real end-to-end integration tests against local `ThreadingHTTPServer` fixtures — one simulating 429s/403s/404s to exercise real backoff, concurrency reduction, retry-history preservation, and `PARTIAL` status; one serving a real SPA shell to exercise real browser escalation and rendered-content capture. 195 tests total pass on a fresh database (was 141 before this phase); the existing acquisition/crawl/extraction/retrieval code was not touched.

**Manual validation:** ran `kpi-crawler-acquire` live (normal and `--verbose` modes) against a local server that rate-limits and denies specific paths — confirmed the terminal never goes blank during backoff, important events (429/session-retirement/concurrency changes) print immediately, normal mode aggregates and hides per-attempt detail while `--verbose` shows it, and the final `ACQUISITION RESULT` box always prints with a correctly-derived `PARTIAL` status and non-zero evidence path.

**Deliberately not built this phase** (per the explicit Program 1/Program 2 boundary): no extraction, no entity/KPI extraction, no embeddings/chunking, no semantic mapping — those are Program 2/3. No fingerprint-management subsystem (see the follow-up phase below — investigated and added immediately after). No live proxy validation (no proxy infrastructure available in this environment; the pool logic itself is fully tested).

## Fingerprint management follow-up (2026-09-19)

**Why the original implementation omitted it.** The engine was built directly on raw `playwright.sync_api` (`browser_acquirer.py`) — Crawlee itself was never part of the architecture; nothing imported it, and it was not a project dependency (confirmed by inspecting `pyproject.toml`/`uv.lock` and grepping the codebase — the only occurrence of the word "Crawlee" was a docstring name-drop, not a usage). Plain Playwright has no fingerprint-generation or fingerprint-injection API of its own; that capability is exactly what Crawlee's separate `fingerprint_suite` (backed by the `browserforge` library) exists to add on top of it. Since the engine used only bare Playwright, there was no fingerprint mechanism to wire in — hence the honest "not built" entry above, rather than a stub or a home-grown spoofing layer.

**Investigation before changing anything** (as instructed): inspected installed packages (`crawlee`/`browserforge`/fingerprint-related packages: none installed), confirmed the engine uses Playwright directly with no Crawlee dependency anywhere, then installed `crawlee[playwright]==1.10.1` into a throwaway `uv run --with` environment (not the project) to read its actual, current fingerprint API rather than assume one. Found `crawlee.fingerprint_suite.DefaultFingerprintGenerator` (an alias for `BrowserforgeFingerprintGenerator`, explicitly documented in Crawlee's own source as "experimental"). Read Crawlee's own `crawlee/browsers/_playwright_browser_controller.py::_create_browser_context` to see exactly how Crawlee itself applies a generated fingerprint to a Playwright context: `browserforge.injectors.playwright.AsyncNewContext(browser=..., fingerprint=generator.generate(), **options)`. `browserforge` ships a symmetric sync function, `browserforge.injectors.playwright.NewContext`, for sync Playwright (which this engine uses) — same call shape, verified by reading its signature directly rather than guessing.

**What this ruled out:** adopting Crawlee's own `PlaywrightCrawler`/`BrowserPool` orchestration would have meant replacing this engine's session/proxy/adaptive-policy machinery with Crawlee's async equivalents — a full architecture rewrite, not "the smallest correct integration," and not what was asked for. The minimum correct change is to use Crawlee's fingerprint generator plus browserforge's Playwright injector — the same two library calls Crawlee's own controller makes — inside the existing `_BrowserWorker._context_for`, leaving everything else (sessions, proxies, adaptive policy, the engine orchestrator) unchanged.

**What was implemented:** added `crawlee[playwright]` as a real dependency (pulls in `browserforge` and `apify-fingerprint-datapoints` transitively). `_BrowserWorker` (`browser_acquirer.py`) now creates one `DefaultFingerprintGenerator` per browser instance (in `start()`) and, when creating a new session's `BrowserContext`, calls `browserforge.injectors.playwright.NewContext(browser=self._browser, fingerprint=self._fingerprint_generator.generate())` instead of a plain `browser.new_context()`. One fingerprint is generated per session at context-creation time and stored (`_fingerprints[session_id]`); every page opened in that context automatically carries the same injected fingerprint (Playwright contexts, not pages, own the injection), and it is discarded when the session is retired. `enable_fingerprinting: bool = True` is a new `EngineConfig`/`BrowserManager` option with a plain-`new_context()` fallback when disabled, so the mechanism is exercised and verified, not silently mandatory. `BrowserManager.fingerprint_for(session_id)` (thread-marshaled like every other `BrowserManager` method) exposes the generated `Fingerprint` for introspection/tests.

**Tests** (`tests/test_acquisition_engine_fingerprint_integration.py`, 5 tests, real headless Chromium against a real local server, no mocking): fingerprinting is on by default and a session gets a real `Fingerprint` whose `navigator.userAgent` is exactly what the *browser itself* reports back (verified by reading it out of actual rendered page content, not just asking the generator independently); the same session's fingerprint object and browser-reported `navigator.userAgent` are identical across repeated page loads; 8 independently created sessions are checked as a set (not a single pair — a single popular Chrome/Windows UA string can legitimately repeat across draws in real header datasets, so pairwise inequality is the wrong test) to confirm sessions are not all silently handed the same cached profile; the `enable_fingerprinting=False` fallback still successfully acquires content and correctly records no fingerprint; retiring a session clears its tracked fingerprint. All 5 pass, stable across repeated runs.

**Validation:** full suite re-run on a fresh database: **200/200 pass** (was 195 before this follow-up), including the pre-existing browser-escalation test (fingerprinting is now on by default and did not break it).

## CLI completion / operator-experience polish (2026-09-19)

Finished `kpi-crawler-acquire` as a reliable operator interface over the existing acquisition engine — no acquisition/adaptive-policy/proxy/browser architecture changes, purely presentation plus a small number of real gaps found while wiring the CLI up honestly to actual engine/ledger state.

**Real gaps found and fixed (not cosmetic — each was a genuine correctness issue, found by trying to make the CLI honestly reflect real state):**
- The progress ticker's `while not stop_event.wait(interval): emit()` only emits *after* the first full `progress_interval_seconds` (default 5s) — the terminal was genuinely blank for the first 5 seconds of every run, including the fast/common case where the whole run finishes in under 5s and nothing but the final summary ever appeared. Fixed: emit one snapshot immediately, then loop.
- `EvidenceLedger.summarize_run`'s `retries` was `sum(a.retry_number for a in attempts)` — a URL retried 3 times (attempts numbered 0,1,2,3) reports "6 retries" instead of the correct 3, because it sums the index rather than counting attempts beyond the first. Fixed to `sum(1 for a in attempts if a.retry_number > 0)`.
- `RunSummary.discovered` was silently reused to mean "URLs attempted" (`len(last_by_url)`), so a URL found by link discovery but dropped for being off-host or over the artifact budget was invisible everywhere — there was no way to tell "184 discovered, 171 attempted" apart, only one conflated number. Added a real `attempted` field (ledger-derived, unchanged meaning) and had the engine track true discovery (every URL `discover_links` ever surfaces, including filtered-out ones) separately, correcting `discovered` on the final `RunSummary` via `dataclasses.replace` after `summarize_run()`.
- `ProxyPool.report_success` returned nothing, so there was no way to detect *recovery* (unhealthy → healthy) versus an already-healthy proxy succeeding again — needed to emit a "proxy recovered" event exactly once per recovery, not on every request. Now returns `bool`.

**New contract addition:** `AcquisitionState.INTERRUPTED` (migration `0011_acq_runs_interrupted_status.sql` extends `acq.runs`'s status check constraint) — a run-level-only status for a Ctrl+C'd run, distinct from FAILED (nothing succeeded) and PARTIAL (ran to completion with mixed results), since an interrupted run may have acquired plenty and simply been cut short. `AcquisitionEngine.request_shutdown()` (thread-safe, callable from a signal handler) stops scheduling new BFS waves and stops retrying a URL already past its first attempt, but never aborts an in-flight request or touches already-recorded evidence — genuinely graceful, not a kill switch.

**CLI (`cli.py`), all backed by real engine/ledger data, nothing fabricated:**
- Run start (🚀) and target (🌐) announced immediately, before the first progress tick.
- Discovery progress (🔎) emitted once per BFS wave (not per URL) when link discovery finds anything new.
- New important events: repeated-timeout escalation, repeated-network-error/5xx escalation (derived from existing per-attempt `retry_number`/`failure_classification`, no new tracking), retry-budget-exhausted, proxy recovery, and a run-outcome announcement ("Run finished: PARTIAL") right before the final box.
- Verbose mode rewritten to the bracketed `[attempt]`/`[url]`/`[method]`/... block format, including a `[fingerprint]` line for browser-method attempts — a short, non-reversible descriptor (`platform:8-char-digest-of-UA`), never the full profile, sourced live from `BrowserManager.fingerprint_for(session_id)` (presentation-only enrichment on `events.AttemptEvent`, never written to the ledger — the stable contract in `contract.py` is unchanged).
- Secret redaction: a regex strips embedded `user:pass@` userinfo from every free-text field before it's printed (headline, detail lines, attempt URL, error message) — the one place this contract could carry credentials is a proxy configured with them in its URL.
- Final summary gained `Run ID`, `Target`, `Attempted`, `Partial` lines, and — for any non-SUCCESS run — a failure breakdown (`RunSummary.by_state`, ledger-derived) and an adaptive-actions breakdown (`EvidenceLedger.adaptive_decisions_for_run`, new ledger method, also ledger-derived) underneath the box.
- Exit codes: 0 SUCCESS, 1 configuration/usage error (matches the existing `kpi-crawler`/`kpi-crawler-retrieval` convention), 3 PARTIAL, 4 FAILED, 5 INTERRUPTED (2 deliberately left to argparse's own usage-error convention).
- Ctrl+C: first SIGINT calls `request_shutdown()` and prints a one-line notice; a second SIGINT restores the previous handler and forces immediate termination (standard "graceful then force" convention). Verified with a real `kill -INT` against a running process, not just a unit test.
- Deliberately still a plain sequential line-printer, no ANSI/curses live-updating status line: this makes "works identically in an interactive terminal, CI, and a redirected file" true by construction rather than needing a detect-and-fall-back branch, and keeps every behavior asserted by a plain string-equality test.

**Tests** (`tests/test_acquisition_engine_cli.py` expanded to 22 tests; `tests/test_acquisition_engine_interrupt_integration.py`, 5 new tests; `tests/test_acquisition_engine_http_integration.py` +4; `tests/test_acquisition_engine_ledger_integration.py` +2; `tests/test_acquisition_engine_proxy.py` +1): startup-event ordering, progress aggregation and format, every important-event type, backoff display, verbose bracket format including fingerprint/evidence/artifact lines, final summary field completeness, partial/complete-failure breakdown rendering (and that it's omitted for clean SUCCESS), secret redaction (proxy credentials never reach any renderer), exit-code mapping, `attempted == acquired + failed` / `discovered >= attempted` consistency guards, real Ctrl+C-equivalent interruption (`request_shutdown()` before a run and mid-run against a real local server with a deliberately slow endpoint, proving in-flight work finishes, no new work is scheduled, the ledger persists `INTERRUPTED` — not just in-memory — and the run never silently reports SUCCESS), and the immediate-progress-tick fix (a 120s periodic interval still produces an immediate snapshot). **229/229 tests pass** on a fresh database (was 200 before this task).

**Manual validation** (real local HTTP servers, real CLI invocations, real exit codes read from the actual process): a PARTIAL run (mixed 429/403/404) in normal and `--verbose` mode; a complete FAILED run (unreachable host, exit code 4); a clean SUCCESS run (exit code 0, no failure breakdown printed); a real `kill -INT` against a running CLI process mid-crawl against a deliberately slow local server, confirming graceful shutdown, correct INTERRUPTED summary, and clean process exit within the expected in-flight-wave time.

**Remaining limitations, honestly recorded:** the repeated-5xx/timeout-escalation and retry-exhaustion events are derived from the existing per-attempt retry loop's own state, not a new dedicated policy subsystem — they fire correctly but are simple threshold checks, not a generalized "failure pattern" engine. No live-updating single-line spinner was built (a deliberate choice, not a limitation — see above). Ctrl+C's "first press" responsiveness is bounded by how long the *current* in-flight HTTP/browser call takes to return (up to the configured timeout) since no request is aborted mid-flight; a genuinely hung request will delay the graceful shutdown until it times out, matching "never abort a request mid-call, never corrupt the ledger" rather than a harder, more invasive cancellation.

## Program 1 run-scoped storage isolation architecture (2026-09-19)

Frozen acquisition behavior and redesigned Program 1 storage so every acquisition run is completely isolated, self-contained, and portable.

**Target structure achieved:**
```
.data/
└── runs/
    └── <safe-site-id>/
        └── <run-id>/
            ├── raw/
            │   ├── html/
            │   ├── json/
            │   ├── pdf/
            │   └── other/
            ├── evidence/
            │   ├── attempts.jsonl
            │   └── adaptive_decisions.jsonl
            ├── manifest.json
            └── program2/
                ├── artifacts.json
                ├── metadata.json
                └── provenance.json
```

**Implementation details:**
- `safe_site_id(url)` sanitizes network locations (ports, special chars) into directory-safe tokens.
- `classify_content_type(content_type, url)` sorts raw artifacts into subdirectories `raw/html`, `raw/json`, `raw/pdf`, and `raw/other`.
- `RunStorage` manages the per-run directory structure:
  - Enforces path containment (`relative_to(run_dir)`) to prevent path traversal escapes.
  - Automatically writes raw artifacts, attempts, and adaptive decisions.
  - Compiles self-contained top-level `manifest.json`.
  - Generates the Program 2 handoff package in `program2/` (`artifacts.json`, `metadata.json`, `provenance.json`), decoupling Program 2 from Crawlee/Playwright/proxy/session internals while preserving the contract.
- Authoritative boundary: PostgreSQL remains the authoritative source for structured ledger metadata and relations; filesystem provides the raw artifact storage and portable run package.
- Full database clean reset verified: schemas `acq` and `app` dropped and recreated cleanly across all 11 migrations.
- Complete test coverage in `tests/test_acquisition_engine_storage.py` proving all 8 target requirements. Full test suite passes (238 passed, 1 skipped).

## Unresolved issues

- No domain behavior, KPI models, relevance, scoring, scheduling, or API has been implemented because those belong to later phases.
- Full `robots.txt` `Disallow` politeness/compliance was intentionally **not** implemented — only the `Sitemap:` directive is read. Respecting crawl-delay/disallow rules is a reasonable future addition but was not part of what this phase asked for.
- `<base href>` is not honored when resolving relative links (uncommon in practice); a page using it would have its relative links resolved against its own URL instead.
- A stale-`raw_storage_ref` fragility exists when an artifact's backing raw file is removed from disk out-of-band while its `app.artifacts` row (content-addressed, immutable) persists: a later `acquire_source` call for the same content dedups against the existing row via `ON CONFLICT DO NOTHING`, and extraction then fails trying to open the now-missing path. The pipeline already surfaces this safely and correctly as a recorded `ExtractionError` (no crash, no silent data loss), so no immediate fix is required, but reconciling or re-materializing a missing raw file for an already-registered artifact is a possible future improvement, not implemented here.
- **(Observed against real fixtures, not fixed.)** The `_table_item` clustering heuristic in `kpi_crawler/extraction.py` (rows must have the exact same non-1 cell count to be recognized) found a table on only 2 of the 8 real, rotated NIRF PDFs (`table_count=0` on the other 6), despite those 6 visibly containing tabular data (e.g. a years-header row followed by aligned figures). No data is lost — every line is still captured as individual, correctly-ordered `text` evidence — this is a coverage gap in a heuristic tuned against a clean, non-rotated synthetic fixture (`tests/fixtures/structured.pdf`), not a crash or corruption. When the heuristic *did* trigger (2/8 real documents), its output was verified correct (11/11 rows properly paired, no misalignment) — so the concern is coverage on this document shape, not correctness. Improving it (e.g. accounting for page rotation in the row/column clustering) is a real, hypothetical future improvement; it was deliberately left alone this phase rather than redesigned in response to a single observation run.
- **(Observed against real fixtures, not fixed.)** The heading/section heuristic (median line height × 1.5) fired exactly once per real document — on the page-1 title only — across all 8 real fixtures, so `structure.section` (and therefore the `canonical_text` prefix) is the same document-title string for nearly every one of the 3,547 evidence rows, giving little differentiation between, say, a "Sanctioned Intake" section and a "Financial Resources" section within the same document. This is a real, measured limitation of a simple relative-height heuristic on densely, uniformly-formatted government-form PDFs (very different from the single-heading synthetic fixture it was validated against), not a bug — nothing is mislabeled or lost, the section context is just uninformative. Recorded as a hypothetical future improvement; not acted on.
- **(From the engineering-review pass, deliberately not changed.)** SSRF exposure is inherent to "fetch whatever URL you're given," which is this tool's actual purpose (including deliberately supporting on-prem/internal targets via `file://` and plain local paths). Blocking private/internal IP ranges by default would be a real behavior change affecting legitimate on-prem deployments and wasn't asked for; operators should not point a crawl at infrastructure they don't trust or control without considering this.
- **(From the engineering-review pass, deliberately not changed.)** `acquire_source`'s parameter is named `max_bytes` while every layer above it (`pipeline.py`, `crawl.py`, `config.py`, the CLI) calls the same concept `max_artifact_bytes`. Each call site maps the two clearly, so this is a minor naming inconsistency, not a functional problem; renaming would touch several files and tests for a cosmetic gain and was left alone.
- **(From the engineering-review pass, deliberately not changed.)** `discover_links` dispatches HTML link-extraction on an exact `content_type == "text/html"` match, so a page served as `application/xhtml+xml` (rare today) would be acquired and stored like any other resource but not crawled for further links. Nothing breaks; it just isn't followed. Broadening the match wasn't requested and XHTML is effectively legacy.
- **(From the engineering-review pass, deliberately not changed.)** When extraction is deduplicated (identical content reached via a second URL), no new `evidence_provenance` row is created for that second URL — provenance for that evidence still points only at the URL where it was first extracted, matching how `artifacts.source_url` also only reflects the first-seen location. The second URL's fetch is still fully durable in `acquisition_events` (with the correct `artifact_id`), just not linked from the evidence rows themselves. This is a characteristic of the existing content-addressed design (extraction is a property of the bytes, not of any one URL that happens to serve them), not a bug; changing it to a many-URLs-per-evidence model would be a real provenance-model redesign that wasn't asked for here.
- **(From the retrieval-baseline phase, deliberately not changed — see `observations.md` for detail.)** No relevance mapping, scoring, deduplication of near-identical evidence text before embedding, reranking, or KPI-category filtering was implemented; this phase measures raw top-K cosine retrieval only. The dominant, measured issue (a handful of ranking KPIs dominating results, traced to a uniform, low-information `canonical_text`/`supporting_context` prefix and 66% exact-duplicate evidence text) is an extraction/evidence-granularity characteristic, not a retrieval-code defect, and fixing it would mean changing evidence generation — explicitly out of scope for this phase.
- **(From the retrieval-baseline phase.)** This sandbox's default PostgreSQL port (5432) is occupied by an unrelated, pre-existing host-level `postgresql.service`, unrelated to this project. `docker-compose.yml` was left with the standard `"5432:5432"` mapping (correct for a normal developer machine); validation in this environment used a standalone container on an alternate host port instead. A developer hitting the same conflict should either stop the conflicting service or override the compose port mapping locally.
- **(From the retrieval-baseline phase.)** The real fixture corpus (8 real NIRF PDFs) produced 0 `visual` evidence rows, so representation-quality comparisons for `visual` evidence could not be made this run; only 2 `table` rows exist, too few to draw a general conclusion about table-representation retrieval quality.
- **(From the Program 1 acquisition-engine phase, deliberately not built.)** Browser-level fingerprinting is handled (see "Fingerprint management follow-up" above), but there is no *proxy*-level anti-detection (residential/mobile IP rotation tied to fingerprint identity, TLS fingerprint matching, etc.) — `proxy.py` tracks health and rotation only. Real proxy infrastructure was never available in this environment to validate against; the pool's rotation/quarantine logic is fully unit-tested, but its behavior against a real upstream proxy (auth, connect failures, latency) is unverified.
- **(From the Program 1 acquisition-engine phase, deliberately not built.)** The BFS traversal processes one full "depth wave" at a time (submit all same-depth URLs concurrently, wait for the wave, then discover the next); a very wide first level (thousands of same-depth links) would submit them all at once rather than streaming work continuously across depths. Not a problem at the scale this was built/tested against; a continuous work-queue scheduler would be a reasonable future improvement if wide sites become common.
- **(From the Program 1 acquisition-engine phase.)** `dynamic_content_likely` is a heuristic (script-byte ratio + visible-text length threshold), the same category of imprecise signal as the existing heading-detection heuristic in `extraction.py`. It was validated against one clear synthetic SPA-shell fixture and one content-rich fixture; real-world sites with partial server-side rendering could go either way. This mirrors the project's existing, accepted practice of shipping and documenting simple heuristics rather than deferring for lack of a perfect classifier.
